# Shared conversation context

Dashboard and Discord use the same `conversationContext` service. Only messages from the authenticated/linked owner's selected conversation are considered. Discord's `!neu` and a new dashboard conversation start without another conversation's memory. Original messages remain in SQLite and in the dashboard; compaction does not delete or rewrite them.

## Default policy

- Input budget: **32,768 estimated tokens**, including system instructions, conversation input, tool definitions and all tool-round items. Output/reasoning allowance remains **4,096 tokens** per model response, outside that input budget. The selected model is unchanged and must support at least the combined budget; the application cannot discover arbitrary model limits automatically.
- Recent context: the newest **complete exchanges**, up to **80 individual messages**, normally user + assistant pairs. Retention is primarily token-based, not a fixed count. Up to 24,000 tokens may be used for originals; system/current-message overhead, 2,000 summary tokens, framing headroom and an 8,192-token tool reserve reduce the actual available amount. The current user message is always included verbatim or rejected clearly if it cannot fit.
- Older context: a **rolling factual summary**, at most 2,000 estimated tokens, stored per conversation with a message-ID cursor. It preserves goals, names, dates, preferences, corrections, decisions and open questions. It is fallible historical context, never a system instruction; newer original messages take precedence. It is not cross-conversation memory or exact retrieval of old details.
- Incremental updates: at most **two summary calls per new turn**, each at most 12,000 estimated input tokens, using the configured model, no tools, `store:false`, a 20-second SDK timeout and no automatic retries. Compaction targets at most 60 recent originals and 75% of the recent-token allowance, leaving room to grow back toward the 80-message limit; this avoids a paid summary on every following turn. Already summarized originals are not sent again. Summaries are reused until more messages leave the raw window. This incurs additional API usage only when updating older context.
- Long-existing conversations catch up in bounded batches. Oversized source exchanges/summary outputs may be explicitly clipped, preserving beginning and end. A partial-context notice is sent in Discord when catch-up is incomplete, a source was clipped or a summary failed. The model receives the same warning. The dashboard API includes context metadata, but the chat UI does not display a context notice. Failed updates do not advance the summary cursor; a 60-second backoff prevents repeated failing calls. Complete original history stays available in the dashboard.
- Tool results above 6,000 estimated tokens become explicitly marked excerpts; the model is told not to infer absence from omitted data. Every subsequent tool round is checked again against the full input budget. If it cannot fit, the turn stops with a bounded-context error rather than sending an unbounded request or breaking tool-call/result pairs.

Token counts are **local estimates**, using the larger of `o200k_base` and `cl100k_base`, small text chunks to avoid pathological tokenizer time, 5% headroom and request framing overhead. They are not exact API billing counts and cannot guarantee fit for every model. Raw payloads are not retained in the bounded token-count cache (hashes/counts only). Set `CHAT_CONTEXT_TOKENS` in the server environment from 8,192 to 65,536 if needed; the default is 32,768. For smaller settings the tool reserve scales down to one quarter of the input budget and summary inputs also respect that setting. Choose a budget compatible with your selected model, including output/reasoning headroom.

A schema-v4 migration adds `conversation_context`; deleting a conversation/user cascades its summary. Reads and post-summary writes recheck ownership/existence, and aborted/deleted conversations cannot be revived by a late summary. Shared conversation locks serialize dashboard and Discord turns. Summary failure does not fail the new conversation turn; missing context is made explicit instead. Summary updates may persist even if the later answer fails because they only describe already committed history. Intermediate tool traces are still only kept during the current turn; the persistent transcript contains user messages and final answers.

References: [OpenAI context-window guidance](https://developers.openai.com/api/docs/guides/conversation-state#managing-the-context-window). The implementation keeps application-owned textual summaries so existing user/assistant transcripts and the configured model remain usable; it does not require provider-persisted conversation state or opaque compaction items.
